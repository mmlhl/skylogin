# 渠道服扫码：从「能用」到「能进游戏」

> 这篇记录 v1.3.2 之后围绕渠道服扫码做的一轮探索。写下来是想留个过程——
> 我们试过什么、错在哪、为什么最后是这个结论。技术细节在
> [04-渠道服扫码](./04-渠道服扫码.md)，这篇只讲思路和坑。

## 起因

一开始工具只支持两类账号：网易官方，和华为（走华为自己的登录接口）。

但光遇在手机上有 B站服、4399 服、vivo 服、九游服……玩家在这些渠道里也有号。
能不能让他们不用打开对应渠道的 App，直接在这个工具里加上？

## 结论先摆出来

| 渠道 | 能加账号 | 能进游戏 | 凭证寿命 |
|---|---|---|---|
| 华为 | ✅ | ✅ | 约 1 小时（启动前自动重签） |
| vivo | ✅ | ✅ | 约 1 小时 |
| B站 | ✅ | ✅ | 较久 |
| 4399 | ✅ | ✅ | 较久 |
| 九游 | ✅ | ✅ | 较久 |
| 应用宝 | ✅ | ❌ | 2 小时，且同号只能一台设备 |

**用法**：打开光遇 → 走到「加好友」界面点扫码 → 用对应渠道的手机 App 扫窗口里的二维码。

## 最关键的一个发现

> **二维码不是我们画的，是游戏自己的。**

用游戏身份（`ma75`）打开官方登录窗时，窗口里那个二维码**渠道服 App 也认**。
扫完 `mpay.dll` 会把渠道账号的信息一起吐回来（渠道名 + 凭证），
我们据此存成一条普通账号，之后的启动链路完全复用。

这个发现把问题从"怎么模拟渠道登录"变成了"怎么把 DLL 给的东西用好"。

## 走过的弯路

### ① 扫完码，游戏说"拿不到票"

第一次成功扫华为时，我们以为搞定了，结果报错。

**原因**：DLL 回调里是**渠道账号**，不是网易账号。MPay 当然没有它的票。
**解决**：认出来是渠道账号，就不去向 MPay 要票，改走渠道自己的凭证。

### ② 渠道 App 只认"游戏码"，不认"平台码"

我们本来想省事，用现成的平台二维码（发烧平台那套）。结果 vivo 直接提示**「不支持」**。

**原因**：两种二维码的建码参数不同，渠道 App 只认游戏身份那份。
**解决**：开窗时强制用游戏身份（`ma75`）初始化。

### ③ 游戏码在服务端换不了票

用游戏码扫完，拿到的 10 位码去加载湾换票，回 `6006`。

试了 B站，**也一样 6006**。所以这不是应用宝特有问题，而是这条路本身对渠道登录不成立。

**教训**：做对照实验很重要——否则会一直以为是某个渠道的特殊问题。

### ④ 「10 位码」和「AAAA 票」是两种东西

抓包才看清：游戏真正发给 `login/ticket` 的是 `AAAAAGgvZhcATRiI` 这种 14 位票，
而二维码确认拿到的是 `4t0vax1y2c` 这种 10 位码。中间还差一步兑换。

拿 10 位码直接换票 → `1306 用户登录失效`。**一度误判成"票有问题"**，其实是用错了东西。

### ⑤ 一个转义字符，让整包解析全空

用户反馈："扫完报『登录包不完整（uid / session 缺失）』"。

查下来：整包里的 base64 padding，有时是 `==`，有时被 URL 转义成 `%3D`。
我们只试了标准 base64 变体，遇到 `%3D` 全部失败，字段就全空了。

**解决**：解码前先做一次 URL 反转义，解出来还要校验"像不像文本"。

**教训**：同一个接口，字段编码形态可能不一致——解析要宽松。

### ⑥ 微信和 QQ 的字段不一样

`extra_data` 里那三个字段，两个渠道不同：

```
微信  login_type=8  session_id=hy_gameid   session_type=wc_actoken
QQ    login_type=2  session_id=openid      session_type=kp_actoken
```

我们一开始把 QQ 那套用在微信上，`uni_sauth` 一直回 `401 invalid access-token`，
换了六种组合都失败——因为**方向错了，不是组合不够**。

**教训**：报错信息很笼统时，先怀疑"用错了对象"，而不是"参数不够全"。

### ⑦ 同一个玩家，存出了两条一模一样的账号

用户先用网页登录加过 vivo，后来用扫码又加了一次。两条记录 id 相同，
界面上**点一个另一个跟着亮**，删除也会一起删。

**原因**：两次存的渠道名不同（`vivo` vs `nearme_vivo`），被当成两个人。
**解决**：渠道名归一 + 给扫码那行单独的行键，两条并存、互不干扰。

### ⑧ 应用宝：服务器认，客户端不认

这是最费劲的一条。

我们打通了微信扫码 → 拿到 openid/atk → `uni_sauth` 返回 `200 ok` → 能取到票。
**但游戏连拒四次。**

排查过程：
- 换渠道名？改成 `huawei` 照样拒
- 换 mpay.dll 版本？4.20 / 4.21 都一样
- 换 `app_channel` 参数？变成"参数错误"

最后查客户端 DLL 的字符串：**里面根本没有 `myapp` 这个渠道名**。
而安卓端正用同一套凭证进游戏——所以**服务器是认可的，缺的是 PC 客户端的实现**。

**结论**：能加账号，但 PC 端进不去。这个能力保留但标注清楚，不让用户白折腾。

### ⑨ 同一份凭证，手机上登一次就作废

应用宝的微信凭证是**单设备**的：手机上再登一次，PC 存的那份立刻失效，
错误是 `access_token is invalid or not latest`（不是过期，是"不是最新的"）。

### ⑩ 有些凭证不能"续期"，越续越糟

我们本来想给所有会话 token 做定时续期。实测发现有一类（`sa=-4`）：

```
续期前  sa=-4，平台上下文，能签票
续期后  sa=3，游戏上下文，票签不出来
```

**续一下反而更烂**。所以现在只续 `sa=3` 那一类，其它一律不动。

### ⑪ 「记住这个号」的槽位，扩不出来

平台有个"记住上次登录"的机制，能让账号过期后免扫。但它一个账号只占一个槽。

试了三个办法想扩槽：
- 换设备号 → 直接 `sauth error`（凭证绑设备）
- 换平台 udid → 能拿到新会话，但槽位还是同一个
- 看接口返回 → 就是一个字段，不是列表

**结论**：槽位数 = 你拥有的网易账号数，扩不了。好在这只影响"凭证丢了之后的兜底"。

### ⑫ 扫码窗里那个小气泡

弹出官方扫码窗时，右上角浮着一个 60×76 的「年龄提示」气泡，正好压住二维码。
官方给了个开关 `mpay_option_show_welcome_tip`，设了没反应。

**解决**：直接找到那个窗口（类名 `MPAY_AGE_TIPS`）藏掉。

## 顺带确认的两件事

**签名算法是对的。** 我们从官方 APK 的 `libYSDK.so` 里找到了签名盐，
又用官方客户端抓到的请求反算了一遍：

```
md5(时间戳 + 盐) = 官方请求里的 sig     ← 逐字符相同
```

**`noncestr` 服务端不校验。** 用空前缀、随便一个字符串都能过——它只是个流水号。

## 想接新渠道？改一处就够

渠道差异全部收在 `internal/app/scanchen.go` 的一张表里：

```go
{Key: "huawei", Label: "华为", Kind: kindSDKInfo, Supported: true,
 Lifespan: "accessToken 约 1 小时（启动前会自动重签）"}
```

步骤是：
1. 扫一次码
2. 看回调里渠道名是什么、凭证是"零散字段"还是"整包"
3. 在表里加一行

界面的说明文字也从这张表生成，前端不用改。

## 一句话总结

这一轮最大的收获不是"多支持了几个渠道"，而是搞清了一件事：

> **我们不是在模拟登录，而是在借用游戏自己的登录能力。**
> 二维码是游戏的、换票是游戏客户端做的，我们只负责把结果接住。

想通这一点之后，很多"为什么这么做不行"就都说得通了。
