# 渠道服游戏内扫码

> 想先看「我们试过什么、错在哪」，可以读 [05-探索与踩坑](./05-探索与踩坑.md)；
> 这篇是逐条记录的技术细节。

## 一句话

**打开光遇，走到「加好友」界面点扫码**，用渠道服的手机 App 扫窗口里的二维码。
扫完 mpay.dll 会把渠道账号的信息一起吐回来，我们据此存成一条普通的渠道账号，
之后点启动就能进游戏。

这是「添加账号 → 渠道服扫码」这个入口在做的事。它和「网易账号 → 扫码登录」
不是一回事：后者扫出来的永远是网易账号，前者扫出来的是**渠道账号**。

## 支持的渠道（2026-11-06）

| 渠道 | 服务端叫法 | 回调里的凭证 | 凭证寿命 | 能进游戏 |
|---|---|---|---|---|
| 华为 | `huawei` | `sdk_info`（openid + accessToken） | **约 1 小时**（每次启动前自动重签） | ✅ |
| vivo | `nearme_vivo` | 整包 | **约 1 小时** | ✅ |
| B站 | `bilibili_sdk` | 整包 | 较久 | ✅ |
| 4399 | `4399com` | 整包 | 较久 | ✅ |
| 九游 | `uc_platform` | 整包 | 较久 | ✅ |
| 应用宝 | `myapp` | 整包 | 2 小时，且同一微信只能一台设备 | ❌ 见文末 |

**华为 / vivo 的凭证只有约 1 小时**，过期后重新扫一次即可（不用换账号）。

### 加新渠道只要改一处

渠道差异全部收在 `internal/app/scanchen.go` 的 `scanChannels` 里：

```go
{Key: "huawei", Label: "华为", Kind: kindSDKInfo, Supported: true,
 Lifespan: "accessToken 约 1 小时（启动前会自动重签）"}
```

- `Kind` 只有两种：`kindSDKInfo`（还要再调一次渠道接口换凭证，目前只有华为）
  和 `kindPackage`（整包直接能用）
- 界面上的说明文字也从这张表生成（`/api/state` 的 `channelScan`），
  加渠道不用改前端

要接一个新渠道，流程是：扫一次 → 看回调 `slot7` 是什么名字、`slot8` 里是
`sdk_info` 还是整包 → 在表里加一行。

## 为什么以前不行

以前扫完只报「拿不到 MPay 票据」就结束了——因为拿回来的是**渠道账号**，不是网易账号，
MPay 当然没有它的票（`GetUserTicket` 回 `code=4`）。

## 现在怎么做的

```
渠道服 App 扫游戏码
      ↓
DLL 登录成功，回调槽位里是渠道信息：
      slot0 = 1181193295205885     ← 华为 uid
      slot7 = huawei                ← 渠道名
      slot8 = 一大段 JSON           ← 关键
      ↓
从 slot8 里挖出凭证：
      slot8.extra_unisdk_data
        └─ extra_data
             └─ sdk_info = { openid, accessToken }
      ↓
用 accessToken 走华为那套接口（和网页扫码登录完全一样）：
      huawei.GetGameSession(accessToken, appID, phoneType, dev)
        → playerId / gameAuthSign / ts / playerLevel
      ↓
存成一条普通华为账号（Channel 留空就是华为）
      ↓
启动链路完全复用，不需要为它写第二套发票逻辑
```

## 入口

添加账号 → 网易账号 → **「渠道服扫码（试验）」**

这个入口会**强制用游戏身份（ma75）开窗**，不受设置里「开发者调试」的 game id 影响。

## 限制

| 项 | 说明 |
|---|---|
| 渠道 | 目前只认 `huawei`；其它渠道会明确报「暂不支持 X 渠道」 |
| 凭证寿命 | 来自渠道的 `accessToken`，本身有时效；过期后要重新扫一次 |
| 记录形态 | 和「华为账号」网页扫码存出来的一模一样 |

第二条是已知短板：网页扫码那条路拿到的是华为的 ST，可以自己续期；
这条路只有 accessToken，续不了。所以它更适合"临时加个号"，不适合长期当主力。

## 其它渠道要怎么接

同一套流程，差别只在 `sdk_info` 里有哪些字段。需要先拿到样本：

1. 各个渠道服的客户端（B站、4399、vivo、小米…）扫一次游戏码
2. 把 `%APPDATA%\SkyLogin\channel_login_slots.json` 收下来
3. 看它的 `sdk_info` 里是 `uid` / `session` / `access_token` 中的哪些
4. 按那个渠道现有的登录链路（`internal/app/login.go` 里各渠道的分支）对上字段

⚠️ 那个 json 里是**真实凭证**，只在本地看，不要提交。

- `internal/app/mpaylogin.go`：`StartChannelScanLogin()`（强制 ma75）

## 关键发现：华为的 `ts` 只认 10 分钟

拿存下来的账号去拿登录包，服务端直接拒绝：

```
param [ts:1793883457516] should between [1793883531295, 1793884131295]
```

窗口正好 600000 毫秒 = **10 分钟**，而且起点是"现在"——也就是说
**ts 必须是刚生成的**，存下来的账号放几分钟就作废。

所以扫完能进游戏，但十分钟后再启动就进不去了。

## 解决办法：启动前用 accessToken 重签

`accessToken` 本身没那么快过期（实测 6 分钟后还能用）。所以每次启动前：

```
存着的 accessToken → huawei.GetGameSession → 新的 gameAuthSign + ts
```

实现：`internal/app/refresh.go` 的 `refreshChannelScannedAccount()`，
`refreshAccount()` 里判断"没有 ST 但有 accessToken 且来源是 channelscan"就走它。

实测：

```
华为 95205885：渠道凭证已刷新（ts 换新）
登录包成功 ✅
```

## 现在的寿命

| 环节 | 寿命 |
|---|---|
| ts / gameAuthSign | **10 分钟**（必须每次启动前重签） |
| accessToken（重签的钥匙） | 未知，至少几小时（还在观察） |

所以这个账号能反复用，直到 accessToken 过期；过期后要重新扫一次。
要彻底解决，得找到"用 accessToken 换华为 ST"的接口——目前没找到。
## 试过的续期办法（2026-11-05，都不行）

想用 accessToken 换一个能长期用的凭证（最好是 ST），挨个试了华为的 OAuth 入口：

```
POST oauth2/v3/token  grant=refresh_token        → 1101 missing required parameter: client_secret
POST oauth2/v3/token  grant=service_token        → 1101 invalid grant_type
POST oauth2/v3/token  grant=client_credentials   → 1101 invalid client_secret
POST oauth2/v3/silent_token  + accessToken       → 参数不对，但方向本身也不成立
```

结论：**`ST → access_token` 是单向的**，反过来没有入口。要续期必须有
`client_secret` 或 `refresh_token`，渠道服扫码这两样都拿不到。

所以这条路的天花板是：**accessToken 活多久，账号就能用多久**。

## 过期后的表现（已处理）

accessToken 过期时，`refreshChannelScannedAccount` 会失败。对渠道服扫码的号
**不能"拿旧凭证凑合"**（旧 ts 只有 10 分钟，必然失败），所以直接：

- 标记账号 `expired`
- 界面提示"需要重新扫码"
- 启动被拦下，不会出现莫名其妙的 401

（华为网页扫码的号不受影响：它们有 ST，刷新失败时仍可先用缓存的那份试一次。）

## 2026-11-05 晚：二维码能不能自己建（结论：能建，但换不到账号）

想省掉官方登录窗，验证过四条路，全部记在这里。

### 1. 自建"游戏码"能被渠道 App 扫

`mpay/api/qrcode/create_login`（`game_id`=光遇长 id、`jf_game_id=ma75`、
`qrcode_channel_type=2`）建出来的码：

| 扫码 App | 结果 |
|---|---|
| vivo | 扫得动，状态 0→1→2，`login_channel=nearme_vivo` |
| 华为 | 扫得动，状态 0→1→2，`login_channel=huawei` |

也就是说**二维码本身完全可以自己建**，跟 mpay.dll 没关系。

### 2. 但 `qrcode/query` 只回一个 code

两个渠道的响应都长这样，没有任何渠道凭证：

```json
{"login_info":{"code":"…","login_channel":"huawei","src_client_country_code":"CN","src_client_type":1},
 "qrcode":{"status":2,"uuid":"…"}}
```

而官方 DLL 回调里的 `slot8` 是**整套登录包**（`extra_unisdk_data` →
`SAUTH_STR` = `gameid=ma75&login_channel=huawei&app_channel=huawei&…`）。
两侧对比说明：**这套数据不是从 `query` 拿的**，DLL 走的是别的口子。

### 3. 游戏码换不了票

拿扫到的 code 走加载湾换票（`ExchangeTicketWithSid`）：

```
code=6006  msg=Mpay qrcode login request failed, invalid http status.
```

vivo / 华为都一样。原因是上下文错位：码建在 ma75 游戏上下文里，
加载湾换票走的是 a50 托管上下文。

### 4. 托管码渠道 App 不认

换成 `game_id=a50 + dst_jf_game_id=ma75`（界面里「扫码登录」用的那套）：
vivo 直接提示**「不支持」**。渠道 App 只认游戏码。

### 结论

```
渠道 App 只认游戏码
游戏码只有官方 DLL 能换成渠道登录包
      ↓
渠道服账号绕不开 mpay.dll
```

所以「渠道服扫码」这个入口保留官方登录窗是必要的。能做的是把点击次数压到最少：
二维码页直接出来（`mpay_option_disable_not_qrcode_login`）、入口提到「添加账号」第一级。

### 工具

`skylogin.exe --qr-probe [--qr-probe-hosted] [--qr-probe-seconds N]`

不加载 mpay.dll、不开窗口，自己建码 → 存 PNG 并打开 → 轮询 → 把整条
响应和「能不能换票」写进 `%APPDATA%\SkyLogin\qr_probe.log`。
换渠道、验证服务端行为时用它，比反复开官方窗快得多。
## 实测：华为渠道服的 accessToken 只活约 1 小时

用 `--probe-channel-token` 每 30 分钟探一次（2026-11-05 晚）：

```
20:57  扫码添加（accessToken）
21:11  ok    仍可用，新 ts=1793884307666
21:41  ok    仍可用，新 ts=1793886060241
22:11  ok    仍可用，新 ts=            ← 返回里已经没有 ts 了
22:41  ok    仍可用，新 ts=
23:00  刷新失败：getGameAuthSign 缺少字段
```

**从扫码到彻底不能用，大约 1 小时。**

### 一个坑：接口 200 不代表还能用

22:11 那次 `GetGameSession` 照样返回 200，只是响应里**没有 `ts` /
`gameAuthSign` 了**。当时的探测只看 `err == nil`，就把它记成了 `ok`，
日志因此骗了我们一次。

现在探测的判断改成：

```
err != nil            → fail
ts 或 gameAuthSign 为空 → fail（半失效）
否则                   → ok
```

启动路径同理：`refreshChannelScannedAccount` 里校验字段，缺了就当失败，
不会拿着半截凭证去撞 `401 auth fail`。

### 结论

| | 华为渠道服扫码 |
|---|---|
| 能进游戏 | ✅ 扫完立刻能进 |
| 能不能反复启动 | ✅ 1 小时内随便启动（每次启动重签 ts） |
| 能不能长期 | ❌ **到 1 小时就没了，只能重扫** |

原因前面写过：`ST → access_token` 是单向的，而渠道服扫码只给 accessToken，
拿不到 ST，也就没有续期的根。所以这个入口只能定位成**临时加号**，
真正常用的号还是得走「华为网页扫码」（那条存的是 ST）。

## 2026-11-05 深夜：vivo 也通了（靠"整包"而不是 sdk_info）

用官方登录窗（ma75）拿 vivo 扫了一次，回调里 `slot7=nearme_vivo`，
`slot8` 里**没有** `sdk_info`，但有：

```
extra_unisdk_data = {
  "SAUTH_STR":  "…"   // base64 → gameid=ma75&login_channel=nearme_vivo&…&sessionid=…
  "SAUTH_JSON": "…"   // base64 → {access_token, sessionid, udid, sdk_version, …}
}
```

也就是说：**华为给的是零散字段（openid + accessToken），vivo 给的是拼好的整包**。
整包里的 `SAUTH_JSON` 就是 uni_sauth 的请求体，直接发过去就行：

```
POST mgbsdk.matrix.netease.com/ma75/sdk/uni_sauth
  → {"code":"200","status":"ok","sdkuid":"ccbd…","unisdk_login_json":"…"}
```

响应里的 `unisdk_login_json.oauth2` 还带了 `access_token`（约 3 天）和
`refresh_token`（约 30 天）——这点比华为那条（accessToken 几小时）好得多，
以后可以研究用 refresh_token 续期。

### 所以代码改成"整包优先"

按渠道一个个对字段是走不远的（每来一个渠道就要加一段）。现在的规则：

1. 回调里能取出 `extra_unisdk_data` 就原样存进账号的 `unisdk_data`；
2. 登录时把它解出来的字段**盖到我们自己的 SAUTH 上**（`buildPayload`）；
3. `op14` 的 `login_channel` 用整包里那个服务端渠道名（`nearme_vivo`），
   不是账号文件里的 key（`vivo`）。

以后小米 / OPPO / B站 只要扫码能过，这边不用再写适配。

### 踩到的坑：同一个玩家存出两条记录

vivo 之前用网页登录加过一次（`channel=vivo`），扫码这次服务端叫 `nearme_vivo`。
`saveAccount` 按 `(player_id, channel)` 匹配，两个名字不同就追加了一行 ——
列表里出现两条一模一样的账号，**点一个另一个跟着亮**（两行的 id 都是 player_id，
删除也会一起删）。

修法：扫码行带一个**行键**（`row_key = "<uid> · 扫码"`），存储和路由都按它来算，
和网页登录那行彻底分开 —— 两条可以并存、各自选中/删除/启动，互不覆盖。
渠道名另外统一走 `channelKeyOf`（nearme_vivo → vivo），避免同一玩家因为名字不同
被当成两个人做凭证同步。

（第一版是"合并成一行"，用户反馈要两条，所以改成现在的行键方案。
被合并掉的那条网页登录记录凭证已经没了，需要重新用「vivo账号 → 网页登录」加一次。）

### 工具

`skylogin.exe --probe-channel-package` 拿 `channel_login_slots.json` 离线验证整包
（真发一次 uni_sauth），通了就直接把账号存回来 —— 不用每次重新扫码。

## 2026-11-05 深夜：refresh_token 续不了期（有对照实验）

uni_sauth 的响应里每个渠道都带 `oauth2.access_token` / `oauth2.refresh_token`，
看着像"统一续期"的出口。实测**不是**：

| 请求 | 回答 |
|---|---|
| 空 sessionid + refresh_token + grant_type=refresh_token | `400 invalid param: sessionid` |
| 假 sessionid + refresh_token | `401 auth fail` |
| 两个都空（对照） | `400 invalid param: sessionid` |
| sessionid 直接填 refresh_token | `401 auth fail` |

第一次试的时候用"原 sessionid + refresh_token"是 200，差点误判——那是因为
**sessionid 本身还没过期**，refresh_token 根本没被用上。加了对照组才看清。

另外 `/sdk/uni_refresh_token`、`/sdk/oauth2/token` 都是 404，没有独立换发口。

### 顺带量到两个寿命

```
access_token   71 小时（QQ 那次）
refresh_token  719 小时（约 30 天）
渠道 sessionid vivo 实测约 1 小时（22:23 拿的，23:24 就 401 token expired）
```

也就是说：**游戏登录认的是渠道 sessionid**，它一过期就得重扫；那两个 oauth2
token 是网易自己发的东西，跟渠道 session 不是一回事。

下一步如果要续期，方向只能是"用 oauth2 token 直接走票据链路"（类似网易账号的
mpay token），而不是拿它去换渠道 session。

## 渠道对照表（2026-11-05 深夜实测）

用官方登录窗（游戏身份 ma75）扫同一张码，不同渠道 App 的结果：

| 渠道 | 服务端渠道名 | 回调里的凭证 | 加账号 | 能进大厅 |
|---|---|---|---|---|
| 网易 | `netease` | MPay token | ✅ | ✅ |
| 华为 | `huawei` | `sdk_info`（openid + accessToken） | ✅ | ✅ |
| vivo | `nearme_vivo` | 整包（有 access_token） | ✅ | ✅ |
| B站 | `bilibili_sdk` | 整包 | ✅ | ✅ |
| 腾讯 / QQ | `myapp` | 整包（只有 sessionid + openid/openkey） | ✅ | ❌ |

`myapp` 的现象：我们这边每次都能取到票并送回（op14 里 `login_channel=myapp`），
但游戏**连续四次都拒收**，一直停在等票的画面，最后放弃应答。其它三个渠道
第一次就进。

也就是说：**能加到账号 ≠ 能进游戏**。渠道凭证能不能换票，还要看 PC 客户端
认不认这个渠道。目前确认可用的是 华为 / vivo / B站。

## 2026-11-06 凌晨：应用宝（微信扫码）自己登录能通，网易那关过不去

光遇确实有应用宝版（idv 的渠道目录里那条）：

```json
{"package_name":"com.tencent.tmgp.eyou.eygy","game_id":"ma75","app_channel":"myapp",
 "myapp":{"channel":"1109425751","wx_appid":"wx365db603f56bf4da"}}
```

### 已经把微信扫码这段做通了（纯 HTTP，不用浏览器）

```
1 GET ysdk.qq.com/auth/wx_scan_code_login     取签名参数（sig = md5(ts + 盐)）
2 GET open.weixin.qq.com/connect/sdk/qrconnect  换二维码 + uuid
3 GET long.open.weixin.qq.com/connect/l/qrconnect 轮询
4 GET ysdk.qq.com/auth/wx_verify_code          wx_code → openid/atk/pf/pfKey/rtk
```

三个坑：

- 签名盐藏在 idv 的 pyc 默认参数里，不是猜出来的常量
- `appid` 要传**微信 appid**，不是 offerid
- 微信确认后回的是 `wx_errcode=405` **加** `wx_code`，先判 code 再判状态码

实测拿到：`openid`、`atk`（2 小时）、`pf`、`pfKey`、`rtk`。

### 但网易不认

用这份凭证按扫码那次的格式拼整包，发 uni_sauth，**六种拼法全部**：

```
{"code":"401","status":"auth fail","debug_message":"…invalid access-token…"}
```

试过的组合：sessionid 用 atk / rtk / openid；session_type 用 kp_actoken /
kp_accesstoken；openkey 用 atk / rtk / 空。错误信息一模一样——说明校验根本
没走到我们变化的那些字段上，网易那边对应用宝渠道还有一层（很可能要 SDK
自己生成的那个 32 位 sessionid，或者服务端另有一条验证链）。

### 进展：微信三元组对上了，uni_sauth 过了

后来对着 idv 的源码发现：微信和 QQ 的 `extra_data` 三元组不一样，之前
拿 QQ 的 `openid/kp_actoken` 去喂微信的 `atk`，所以一直报 invalid access-token。

```
微信  login_type=8  session_id=hy_gameid  session_type=wc_actoken
QQ    login_type=2  session_id=openid     session_type=kp_actoken
```

换成微信三元组后 **uni_sauth 一次通过**（`code=200`），账号能存、能取票。

### 但客户端还是不认这张票

op14 把票交给游戏后，游戏连问四次都没接受（和渠道登录失败那次一样），
最后放弃。B站/vivo/4399/华为 都是第一次就进。

### 为什么 idv 能行

idv 根本不走 op14：它把整包写进**游戏本地的 MPay 账号库**
（`%APPDATA%\Netease\Mpay\*-g-{gid}-64-mpay.db`），游戏启动时读到就
以为已经登录了。写库用它自带的 `idv-db.wasm`（30MB）。

这条路我们没有实现，而且依赖它的 wasm 会牵进 GPL 授权问题。

### 结论

应用宝渠道：**能加账号、能取票，但 PC 客户端不接受它的票**。
能进大厅的仍然是：华为 / vivo / B站 / 4399。

## 2026-11-06 凌晨：签名盐的出处找到了（官方 YSDK 库）

之前那个签名盐的来源一直是个疑问（从第三方工具里看到的）。现在从**光遇应用宝版的官方 APK** 里挖到了原文：

```
光·遇_0.16.7.apk
  lib/arm64-v8a/libYSDK.so
    .rodata  file=0x195d0  va=0x195d0  len=96
    "0123456789abcdef0123456789ABCDEF445B2EB80C3737BE5C2F3668B46D3E96"
    "5C2F##3[6$^(68#%#D3E96;]35q#FB46"
```

也就是说这是**腾讯 YSDK 自带的互操作性常量**，写死在 SDK 里，不是谁私有的东西。
引用它属于"为了与官方客户端通信所必需"，跟用什么开源协议无关。

顺带验证：`noncestr` 服务端**完全不校验内容**——空前缀、任意串都能拿到 `ret=0`。
所以代码里用的是自己的前缀（`skylogin-unisdk-bridge`），不再借用别人的水印串。

### 应用宝 APK 里没有 YSDK

单独查了 `应用宝_9.2.9.apk`（42MB，61650 个类）：

```
wx_scan_code_login    0 处
wx_verify_code        0 处
qq_verify_login       0 处
QQCodeLogin           0 处
5C2F##3               0 处
```

YSDK 是**跟着游戏包走的插件**（抓包里能看到 `ysdk_plugin_version=102`、
`pkgname=com.tencent.ysdkcore`），不在应用宝本体里。

### 安卓抓包对照（314 条）

在光遇应用宝版里走了一遍 QQ 登录，抓到关键几发：

```
GET ysdk.qq.com/auth/qq_verify_login?channel=10095285&offerid=1109425751
    &atk=11878E24C90BCFD7124DD65565592485
    &ptk=22B1417BF3C8E45C9F82FD0E0B306EE0
    &loginType=1&platform=desktop_m_qq_m&isCheckATK=1&isCheckPTK=1

POST mgbsdk.matrix.netease.com/ma75/sdk/uni_sauth        200
```

和之前 PC 扫码那次拿到的回调逐字对比：

| | PC 扫码回调 | 安卓 qq_verify_login |
|---|---|---|
| sessionid | `11878E24C90BCFD7124DD65565592485` | atk 同值 |
| openkey | `22B1417BF3C8E45C9F82FD0E0B306EE0` | **ptk** 同值 |

结论：QQ 渠道是 `sessionid = atk`、`openkey = ptk`。
（之前参考的实现里把 `openkey` 写成 atk，那条对 QQ 是错的。）

### 官方 YSDK 的签名是两段式

真实请求带的是：

```
sig=8E421F9357048AFB7228AC1F8B1DDCFD          32 位，MD5
sf=4F1FCE52…D52957                            512 字节，RSA
X-Gas-Nonce / X-Gas-Timestamp                 uni_sauth 还多这两个头
```

我们用的 `md5(ts+盐)` 只是其中一个接口的简化签法，够用即可，不是全局密钥。

### PC 端结论没变

安卓端同一套 `app_channel=myapp` 能 `uni_sauth` 200 并进游戏；
PC 端取票成功但游戏连拒 4 次，且 PC 的 `mpay.dll` / `NtUniSdkMpay.dll`
里搜不到任何 `myapp` 字样。**差别在客户端有没有实现这个渠道，不在凭证。**

### 决定性验证：我们的签名算法和官方完全一致

第二次抓包（安卓端走微信登录），拿到官方 `wx_verify_code` 请求：

```
GET ysdk.qq.com/auth/wx_verify_code
    ?channel=10095285&code=041z600w3zIg483foQ1w3UFuVj1z600w
    &offerid=1109425751&loginType=1&platform=desktop_m_wechat
    &wx_appid=wx365db603f56bf4da&appid=wx365db603f56bf4da
    &version=2.2.2&timestamp=1793899580762
    &sig=80BB32B3F81C1A778D307BB039BEAFCB
    &sf=2CA9ED7B…（512 字节 RSA）
```

拿它自己的 timestamp 和签名盐算一遍：

```
md5("1793899580762" + "5C2F##3[6$^(68#%#D3E96;]35q#FB46")
  = 80BB32B3F81C1A778D307BB039BEAFCB     ← 和官方 sig 逐字符相同
```

也就是说我们代码里的签名算法 **就是官方客户端的算法本身**，
不是"从第三方工具抄来的近似实现"。盐和算法都有官方出处，MIT 协议没问题。

### 应用宝在安卓端根本不建二维码

这次抓包里 **没有任何 `wx_scan_code_login`**，也没有 `qrconnect`。
官方用的是**微信 App 授权**（拉起微信 → 确认 → 回调带 code）：

```
微信 App（SendAuth）→ code=041z600w3zIg483foQ1w3UFuVj1z600w
                   → GET ysdk.qq.com/auth/wx_verify_code?code=…
                   → openid=osGRys6k_lXbj8AoX55JLRRXTRJ4 + atk
```

**所以 `noncestr` 在官方流程里压根不存在**——它是我们为了在 PC 上"自己画二维码"
才需要的东西（走的是微信公开的 qrconnect 流程）。这也说明用它自己的前缀完全正当。

顺带：官方请求带 `sf`（512 字节 RSA），但我们不带也能过——服务端目前不强制。

## 2026-11-06 深夜：搞清楚"票"的两种形态，以及 PC 为什么进不去

### 两种"票"，别搞混

| 形态 | 例子 | 从哪来 |
|---|---|---|
| 10 位码 | `4t0vax1y2c` | 二维码 confirm_login 之后 `login_info.code` |
| AAAA 票 | `AAAAAGgvZhcATRiI` | 平台 `create_ticket` / 加载湾换票之后的票 |

抓包里游戏真正发给 `login/ticket` 的是 **AAAA 票**：

```
POST /mpay/api/users/login/ticket
  ticket=AAAAAGgvZhcATRiI&game_id=…-g-ma75&jf_game_id=ma75&device_id=…
```

拿 10 位码直接调 `login/ticket` 必然 `1306 用户登录失效`——**B站 的码也一样**，
所以之前"用 B站 做对照"的结论是无效的，不是应用宝特殊。

### 加载湾换票只对"手机扫平台码"有效

`10 位码 → ExchangeTicketWithSid → AAAA`，这条路：

| 账号 | 结果 |
|---|---|
| 手机扫平台码（网易账号） | ✅ 能换 |
| B站 渠道登录的码 | ❌ 6006 |
| 应用宝 渠道登录的码 | ❌ 6006 |

也就是说：**渠道登录拿到的 10 位码，没法在服务端换成 AAAA 票**。

### 那游戏是怎么进的？

游戏拿到 op14 里那个 10 位码之后，是**它自己的 mpay.dll 按渠道去换**的——
这正是"按渠道实现"的那部分代码。

- B站 / vivo / 4399 / 华为：客户端会换 → 进得去
- 应用宝（myapp）：客户端不会换 → 连拒 4 次

配合之前查到的：PC 的 `mpay.dll` / `NtUniSdkMpay.dll` 里搜不到任何 `myapp` 字样。

### 结论（可以定了）

应用宝在 PC 上进不去，不是凭证问题、不是票据问题，是
**PC 客户端没有实现应用宝渠道的换票代码**。要绕过，只能像 MITM 那套工具一样
直接改写游戏本地状态（mpay.db），那是另一套架构 + GPL 约束。

### 顺手记下的两个坑

- 应用宝微信 atk **单设备有效**：手机上再登录会让 PC 存的那份失效，
  报 `invalid credential, access_token is invalid or not latest`
- `mpay.dll` 的 `UILessTokenLogin(uid, atk)` 会按 token 形态判断登录类型，
  应用宝 atk 被判成 `login_type: "unknown"`，直接失败
