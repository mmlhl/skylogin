# 还没验证的几件事

> 这里每一条都是**推测**，不是结论。每条都写了"怎么验"。

## A. 临时通行证的有效期，是不是"从开始时间往后数固定天数"

**推测**：是。开始时间一推后，有效期就跟着推后。

**依据**：开始时间刷新后，新证立刻能用；过期时报的是"用户登录已失效"。

**没验证**：没有"一直不换，看它第几天失效"的记录（要放几天才知道）。

**怎么验**：留一条不换的，每天探一次，记下失效那天的日期；再看换过的是不是从换的那天重新数。

**影响**：如果成立，续期就是可靠的；如果服务端还看"第一次登录"的时间，那续期也有上限。

---

## B. 一直续下去，会不会被服务端掐掉

**推测**：不会，只要能续就一直有效。

**没验证**：我们只证明了"换一次，开始时间会更新"，**没有跨越过一次真正过期的节点**。

**风险**：服务端可能有"同一会话最多续 N 次"或"总时长上限"的暗规则。

**怎么验**：挑一个号，每天换一次，连着两周，看哪天突然开始报"用户登录已失效"。

**现状**：代码按"能一直续"实现。就算猜错了，也只是回到"提示重新扫码"，不会更糟。

---

## C. 长期通行证换一次会不会变成临时证

**结论：已验证，确实会。**（已从"猜测"移到 `02-实锤-滚动续期.md`）

```
原来的：sa=-9（长期）
换完的：sa=3 （临时）
```

而且原来那张不会被弄坏，仍然可用。

**所以代码里"长期证一律跳过"的做法是对的。**

---

## D. 同一个账号换台设备登录，能不能多一个"记住位置"

**推测**：不能。位置是绑平台账号的，跟设备无关。

**依据**：换设备时用凭证会被直接拒绝（`sauth error`），说明凭证绑设备；
而位置是跟着平台账号走的。

**没验证**：没有"同一账号在另一台设备上用密码真登一次 → 换会话 → 看平台账号变没变"的完整记录。

**怎么验**：需要输一次密码，在另一台设备上登录，然后比对新会话对应的平台账号 id。

---

## E. "记住位置"能保留多久

**推测**：会保留一段时间，可能几天到几周。

**没验证**：没有"放着一个位置不动，每天看一眼"的记录。

**怎么验**：让一个位置放着不扫，隔几天查一次，看还在不在。

---

## F. 有没有"正规"的换长期证接口

**推测**：可能有，但我们没找到。

**依据**：官方 DLL 的回调里出现过 `EXT_ACCESS_TOKEN`，但拿到手几分钟就失效。

**没验证**：没在 `mpay.dll` 的字符串表里找到 refresh / renew 之类的接口。

**怎么验**：翻 DLL 里的网址字符串，逐个试。

---

## G. 平台账号除了"网易账号"，还有没有别的区分维度

**推测**：可能还有 `app_id`（游戏）、客户端类型、地区。

**没验证**：`app_id` 一直是 63，没试过别的。

**怎么验**：用别的小游戏的 `app_id` 调一次，看"记住位置"是不是独立的。

---

## 试过但绕不过去的两条（已验证失败）

### ① 用一张现签的票冒充"扫码的 code"去写位置

想法：`ticket` 接口收 `code` 参数，如果它也认 `AAAA` 开头的票，那不用扫码就能往位置里塞号。

结果：

```
把票当 code 用 → 6006 MPay qrcode login request failed, invalid http status
位置没变（还是原来那个号）
```

**行不通。**

### ② 让扫码号的临时证也能换平台会话（那样每个号都能有位置）

想法：换平台会话时把参数换着花样试，也许临时证也能过。

结果（同一张临时证试了 5 种）：

```
基线                  → 1000 sauth error
get_access_token=0    → 1000 sauth error
channel=shenhe        → 1000 sauth error
不传 app_channel      → 500  服务器繁忙中
gameid=ma75           → 1000 sauth error
```

**行不通。** 临时证就是换不出平台会话。

### 结论

**"位置"的数量确实只能靠"多一个能登录平台的账号"来增加，没有别的捷径。**

但反过来说：能登录平台的号 = 有长期证的号 = 本来就不会过期，
所以对这类号来说"位置"其实是多余的。

真正需要位置的只有**纯扫码的号**，而它们恰恰开不出位置——
所以主力方案必须是**滚动续期**，位置只是兜底。
