# 应用宝（myapp）渠道

> 腾讯应用宝服的登录接入。微信、QQ 两条扫码链路**都是纯 HTTP**——
> 不开窗、不需要浏览器、不需要代理。
>
> 实测环境：光·遇应用宝版 `com.tencent.tmgp.eyou.eygy` 0.16.7，YSDK 2.2.2，
> 2026-11-10 全程验证并进入游戏大厅。

---

## 一、概览

| 项目 | 微信 | QQ |

| 登录方式 | 微信扫码 | 手机 QQ 扫码 |

## 二、微信链路

```
① GET ysdk.qq.com/auth/wx_scan_code_login   申请扫码会话，拿签名参数
② GET open.weixin.qq.com/connect/sdk/qrconnect  换二维码图 + uuid
③ GET long.open.weixin.qq.com/connect/l/qrconnect?f=json&uuid=…  长轮询
④ GET ysdk.qq.com/auth/wx_verify_code       用 wx_code 换 atk / rtk / openid / pf
⑤ GET api.weixin.qq.com/sns/oauth2/refresh_token  续期（只要 appid + rtk）
```

**签名**：`sig = md5(str(ts) + 盐)`，`ts` 是**秒**。

**轮询语义**：

| `wx_errcode` | 含义 |
|---|---|
| 405 | 已扫待确认（注意：**不是 0**） |
| 403 | 用户取消 |
| 402 | 二维码失效 |
| 408 | 等待超时（长轮询正常现象，继续等） |
| 带 `wx_code` | 已确认，可以换凭证了 |

> 判断顺序很重要：**先看有没有 `wx_code`，再看状态码**。
> 微信确认后返回的是 `405 + wx_code`，先看状态码会把"确认成功"当成"扫了没确认"。

**寿命**：atk 7200 秒，rtk 30 天且每次刷新都会滚新 → 只要用户 30 天内启动过，就能一直续。

## 三、QQ 链路

```
① GET openmobile.qq.com/oauth2.0/m_authorize   拿登录页（返回 JS，不是 302）
② GET xui.ptlogin2.qq.com/cgi-bin/xlogin       建立会话 cookie
③ GET xui.ptlogin2.qq.com/ssl/ptqrshow         二维码 PNG + qrsig
④ 轮询 xui.ptlogin2.qq.com/ssl/ptqrlogin       拿 code
⑤ POST ysdk.qq.com/cmd/QQCodeLogin             code → atk / ptk / rtk / openid
⑥ GET ysdk.qq.com/auth/qq_verify_login         atk → pf / pfKey
```

### 3.1 第①步：抠 xlogin 地址

`m_authorize` **不回 302**，返回一段 HTML，跳转地址硬编码在 JS 里：

```html
<script>
  var src = "https://xui.ptlogin2.qq.com/cgi-bin/xlogin?…&h5sig=xxx&loginty=6";
  location.replace(src);
</script>
```

正则抠 `var src = "…"` 之后，**必须还原 JS 转义**（`\x3A` → `:`、`\x2F` → `/`、`\x26` → `&`）。

`h5sig` 是服务端生成的，别自己拼。

### 3.2 第④步：`pt_openlogin_data` 是关键

这是整条链路唯一的坎。浏览器的轮询请求长这样：

```
https://xui.ptlogin2.qq.com/ssl/ptqrlogin
  ?u1=http%3A%2F%2Fconnect.qq.com&from_ui=1&type=1&ptlang=2052
  &ptqrtoken=<hash33(qrsig)>&daid=381&aid=716027609&pt_3rd_aid=1109425751
  &pt_openlogin_data=appid%3D716027609%26…%26redirect_uri%3Dauth%253A%252F%252Ftauth.qq.com%252F%26…
  &device=2&ptopt=1&pt_uistyle=35&jsver=3ea7b82c&r=0.975…
```

**`pt_openlogin_data` 的值 = xlogin 地址的整个 query string**（原样，再整体 URL 编码一次）。

服务端从这里读到 `redirect_uri=auth://tauth.qq.com/`，才会把回调生成成：

```
http://auth://tauth.qq.com/?code=<32位hex>&ret=0&pf=…&pfkey=…&auth_time=…&page_type=0
```

**少了它会怎样**：服务端**不报错**，只是静默降级成

```
http://ptlogin4.openmobile.qq.com/check_sig?pttype=1&uin=…&ptsigx=…&s_url=http://connect.qq.com
```

而 `ptlogin4.openmobile.qq.com` 在全球 DNS 里都是 `0.0.0.1`（权威记录，不是污染），
连浏览器都访问不了 → 死路。

> **别去试 check_sig**。`ptlogin2.qq.com` / `ptlogin4.qq.com` 上确实有 check_sig 端点
> （不带参数返回 403），但那条路走不通：它只能换出 `skey`，而 `m_authorize` 生成的
> xlogin 写死了 `pt_skey_valid=0`，服务端仍然要求重新扫码。见第七节。

### 3.3 `ptqrtoken` 与 `hash33`

```go
e := 0
for _, c := range qrsig { e += (e << 5) + int(c) }
token := 2147483647 & e
```

`qrsig` 由 `ptqrshow` 通过 `Set-Cookie` 下发（Domain=ptlogin2.qq.com）。

### 3.4 第⑤步：QQCodeLogin 签名

```
POST https://ysdk.qq.com/cmd/QQCodeLogin
Content-Type: json
Auth-Secret-ID: ysdk
Auth-Request-Time: <ts>            // 秒
Auth-Secret-Digest: base64(HMAC-SHA256(key, "POST\n/cmd/QQCodeLogin\njson\nysdk\n<ts>\n<body>"))

body: {"appID":"1109425751","loginCode":"<32位code>"}
```

响应：

```json
{"code":0,"data":{"ret":0,"openID":"…","accessToken":"…","refreshToken":"…",
 "payToken":"…","expiresIn":"5184000"}}
```

**`expiresIn` 是字符串**，直接按数字解析会报错。

### 3.5 第⑥步：qq_verify_login

参数一个都不能少，缺了回 `11000 missing essential parameters`：

```
channel=10095285  offerid  atk  ptk  openid
loginType=0  loginplatform=1  platform=desktop_m_qq_m
isCheckATK=1  isCheckPTK=1  version=2.2.2
appid  qq_appid  channel_id=10095285  source_channel=10095285  regChannel=00000000
client_hope_switch=1  anti_hope_switch=1  visitor_switch=-1
yyb_install=1  wx_appid  app_version=0.16.7
orientation=2  yyb_vercode=9292130  resolution=3008*1440  app_name=光·遇
yyb_vername=9.2.9  ysdk_plugin_version=102  pay_os=36  is_cloud_env=0
yyb_app=应用宝  sk=default  timestamp  sig
```

**`ptk` 最容易漏**（`isCheckPTK=1` 会校验它）。

签名 `sig = md5(timestamp + 盐)`，注意这里的 `timestamp` 是**毫秒**（微信那套是秒）。

响应里带 `pf` / `pfKey`，拼 extra_data 要用。

## 四、extra_data：微信和 QQ 必须分开

`uni_sauth` 的 `extra_data` 是一段 JSON，两个渠道的**三元组完全不同**：

```json
// 微信
{"login_type":8,"session_id":"hy_gameid","session_type":"wc_actoken",
 "openid":"…","openkey":"<atk>","pf":"…","pfkey":"…","zoneid":"1"}

// QQ
{"login_type":2,"session_id":"openid","session_type":"kp_actoken",
 "openid":"…","openkey":"<atk>","pf":"…","pfkey":"…","zoneid":"1"}
```

拿 QQ 的三元组去喂微信的 atk 会直接失败，**且报错不会提到三元组**，很难排查回去。

`pf` / `pfKey` 只有 QQ 有；微信的 `pf` 来自 `wx_verify_code` 响应。

## 五、续期：微信能永久，QQ 靠保活

### 5.1 微信：真换 token

```
GET api.weixin.qq.com/sns/oauth2/refresh_token?appid=…&grant_type=refresh_token&refresh_token=…
```

**只要 appid + rtk，不需要 client_secret**。rtk 每次刷新都会滚新，30 天窗口一直往后推。

### 5.2 QQ：没有换 token 的接口

试过的（全部失败）：

| 尝试 | 结果 |
|---|---|
| `/cmd/QQRefreshToken`、`/cmd/QQRefreshLogin`、`/cmd/RefreshToken`、`/cmd/QQTokenRefresh` | `api not found` |
| `/auth/qq_refresh_token`、`/auth/refresh_token`、`/auth/qqRefreshLogin` | `not existed cgi name` |
| `openmobile.qq.com/oauth2.0/token`、`graph.qq.com/oauth2.0/token` | `param client_secret is wrong or lost` |
| rtk 当 atk 用 | 不认 |

**根因**：QQ 互联的 refresh 强制要 `client_secret`（服务端密钥），YSDK 没有代理续期接口。

反编译 YSDK 插件包（`com.tencent.ysdkcore`）确认：QQ 模块的
`USER_LOGIN=0` / `USER_CHECK_TOKEN=1` / `AUTO_LOGIN=2` / `WAKEUP_LOGIN=3`
**四种票据全部最终走 `QQUserCheckRequest`（即 `qq_verify_login`）**，没有换 token 的请求类。
微信那边多两个枚举 `WX_AUTO_TOKEN_REFRESH` / `WX_LOCAL_TOKEN_REFRESH`。

### 5.3 但 YSDK 有定时保活（QQ 可能也能永久）

YSDK 里有个定时任务：

```java
// UserTask，任务名 YSDKAutoLogin
public void run() {
    if (!SwitchManager.enabledAutoRefreshLogin()) return;  // 默认 true
    Logger.d("YSDK.UserModule|UserTask", "auto login！");
    UserApi.getInstance().autoLogin();                      // → QQUserCheckRequest
}
```

| 常量 | 值 |
|---|---|
| `TASK_AUTO_LOGIN_DEFAULT_INTERVAL` | 30 分钟 |
| `TASK_AUTO_LOGIN_MIN_INTERVAL` / `MAX` | 10 / 90 分钟 |
| `TASK_NEXT_LOGIN_DEFAULT_INTERVAL` | 5 分钟 |
| `TaskManager.PERIOD` | 60000（1 分钟 tick） |

**它不换 token，只是拿本地 atk 重走 `qq_verify_login`。**
所以「自动刷新登录 token」刷的很可能是 **token 的有效期**（服务端滑动续期），而不是 token 本身。

**我们已模拟它**：`ensureMyappCredential` 里 QQ 分支每次启动调一次 `myapp.QQKeepAlive`，
成功则更新 `pf` / `pfKey` / `last_check`。

- 失败不影响启动（本地 atk 照样能用），只记一条日志；
- 如果滑动续期成立，用户只要 60 天内启动过一次，atk 就一直是活的；
- 如果 60 天后 atk 仍可用，说明成立，把"过期即判死"改成"保活成功就顺延"即可。

> **注意**：保活必须在"离到期还远就直接返回"**之前**执行。
> 60 天内都算"还远"，放后面等于永不执行——这个坑踩过一次。

## 六、落库形态

```go
Account{
    Channel:      "myapp",
    UserID:       openid,
    PlayerID:     openid,        // 与真机抓包一致
    GameAuthSign: atk,           // uni_sauth 的 sessionid
    MyappCred:    "<整份 JSON>", // platform / openid / atk / ptk / rtk / pf / pfkey / atk_expire / last_check
    Source:       "myapp",
    LoginMethod:  "qr",
}
```

`MyappCred` 是**唯一真相**：取票时用它现场拼 `extra_data`，续期后 atk 会变，
必须用最新那份，拿旧的拼会被服务端拒。

## 七、注意的点

### 7.1 发票失败：extra_data 有两份

**现象**：能登录、`uni_sauth` 能过、日志打"已拿到票据"，但游戏反复取票
`#1 → #2 → #3 → #4`，然后 `已应答 4 次仍未成功，暂停应答`，游戏自己退出。

**根因**：`extra_data` 有两份，来源不同：

| 位置 | 来源 | 应用宝账号 |
|---|---|---|
| `uni_sauth` 请求体 | `buildSauth` 的 `custom["extra_data"]` | 拼对了，所以校验通过 |
| 票据 `extra_unisdk_data` | `NewLoginPayloadChan` 的 `playerLevel` 参数 | **恒为空** |

`playerLevel` 对应用宝账号永远是空串（那是网易账号的字段）。

**为什么不报 400**：400 是 `uni_sauth` 那侧的错（`invalid param: extra_data`），
而这次 `uni_sauth` 是过的。日志里没有任何错误码，很容易往别处想。

**修法**：`netsec.ChannelInfo` 有 `ExtraData` / `SessionOverride` 两个字段，两处都优先用。
`buildSauth` 里对 myapp 三处同时对齐：

```go
ch.ExtraData = myappExtraData(d)      // 票据里的 extra_data
ch.SessionOverride = d.ATK            // SAUTH sessionid + 票据 token
custom["extra_data"] = ch.ExtraData   // uni_sauth 请求体
```

**排查口诀**：应用宝账号"能登录、能发票、游戏不认"时，先看票据里的
`extra_unisdk_data` 有没有 `login_type` / `openid` / `openkey`。

### 7.2 渠道判断写死在 start.go

`start.go` 原本写死 `bilibili / m4399 / vivo` 三个渠道走"凭证保活"分支，
应用宝会掉进"华为刷新"分支，报 `账号没有保存 ST，需要重新扫码`。
加渠道时记得同步这里。

### 7.3 轮询别手动设 Cookie 头

`qrsig` 要交给 cookiejar 管。手动 `req.Header.Set("Cookie", "qrsig=…")` 会
**覆盖** jar 里的 `pt_login_sig` / `pt_local_token`，服务端认不出会话。

### 7.4 二维码的传递

后端生成二维码后存进 `loginProgress.QR`，经 `/api/myapp/login/status` 的 `qr` 字段
（PNG base64）下发，前端 `ChannelAskDialog` 显示。

`loginProgress.set()` 必须**保留** QR，否则每次文案更新都会把二维码冲掉。

### 7.5 关对话框要取消

扫码流程最长阻塞 5 分钟。关掉对话框必须调 `/api/channel/login/cancel`，
否则 `tracker.begin` 一直拦着，用户再点就是"没反应"。

轮询用 `PollCtx` / `PollQQCtx`（带 ctx），取消能立刻断开长轮询，
而不是等这次请求自己超时（微信长轮询要 15 秒）。

## 八、排查手册

| 症状 | 先查 |
|---|---|
| 回调地址是 `check_sig` | 轮询少了 `pt_openlogin_data`（3.2） |
| 轮询一直"未扫" | 手动设了 Cookie 头覆盖会话（7.3） |
| `code=-5 subcode=-501` | 把 `ptsigx` 当 code 喂了 `QQCodeLogin` |
| `11000 missing essential parameters` | `qq_verify_login` 少了 `ptk`（3.5） |
| `expiresIn` 解析报错 | 它是字符串（3.4） |
| 能登录、游戏反复取票 | 票据里 extra_data 为空（7.1） |
| 启动报"没有保存 ST" | `start.go` 渠道分支没加 myapp（7.2） |
| 二维码显示不出来 | `loginProgress.set()` 把 QR 冲掉了（7.4） |
| 关掉弹窗后再点没反应 | 没调 cancel 接口（7.5） |

## 十一、附录：结论修正记录

这份文档的结论被推翻过几次，记下来免得后人重走：

| 曾经的结论 | 实际 | 怎么发现的 |
|---|---|---|
| `check_sig` 域名死了，别碰 | 服务活着，是我们带了 xlogin 的旧 cookie 被当普通页面请求 | 裸请求打一次，立刻 302 |
| 浏览器能访问 check_sig，所以只能靠浏览器 | 浏览器也访问不了（`ERR_CONNECTION_RESET`） | CDP 抓响应体，发现 code 在 `ptqrlogin` 响应里 |
| QQ 只能 60 天，没有续期 | 没有换 token 的接口，但有 30 分钟一次的保活 | 反编译 `UserTask` |

**教训**：遇到"浏览器行、代码不行"，先抓浏览器的完整请求逐字段比，
不要凭经验猜域名 / UA / cookie。
